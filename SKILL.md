# Adding a package to pica-nest

Produce a package that validates, plans against the real upstream, and builds —
verified, not assumed.

## Where things live

**`pica-nest` — the source.** One directory per package; everything else is tooling.

```
packages/<mgr>/<id>/manifest     the pica manifest
packages/<mgr>/<id>/build.json   where the payload comes from, which arches
packages/<mgr>/<id>/scripts/     optional lifecycle scripts
packages/<mgr>/<id>/root/        optional files mirrored onto the device
ci/config.json                   the only upstream config: pica ref, release, feed URLs, platforms
ci/nest/                         the tool: python3 -m ci.nest <command>
ci/templates/                    what `nest new` copies
ci/schema/build.schema.json      build.json schema (editor completion)
r/index.json                     hand-written entry descriptor: name, description, index paths
r/<mgr>/index.json               generated by CI — never edit
docs/packaging.md docs/ci.md     the source's own documentation
```

`<mgr>` is the backend whose containers the job fetches (`opkg`, `apk`), or
`pica` for a package with no container. The manifest's `targets` decides which
artifacts come out and must include `<mgr>`. Artifacts are never committed:
they go to the GitHub release named in `ci/config.json`.

**`pica` — the tools.** github.com/miaoermua/pica. The contract is
`docs/standard.md`; where a document and `crates/` disagree, the code ships.

```
crates/pica-pkg-core/src/repo.rs        package_filename(), index schema
crates/pica-pkg-core/src/manifest.rs    what a manifest may declare
crates/pica-pkg-pack/src/build.rs       pica-pack: output layout, version split
crates/pica-pkg-cli/src/candidate.rs    how a client picks an entry
```

Build `pica-pack` from it: `cargo build --release --bin pica-pack`.

**This skill.** `references/` for detail, `scripts/feed_lookup.py` to query feeds.

## The loop

```bash
python3 -m ci.nest new apk/hello --source feed      # feed | github | url | archive
# edit packages/apk/hello/manifest and build.json
python3 -m ci.nest validate                         # static, no network
python3 -m ci.nest plan apk/hello --probe           # resolve upstream, HEAD every URL, no download
python3 -m ci.nest build apk/hello --out out --pica-pack /path/to/pica-pack --keep-stage stage
tar -tzvf out/apk/*.pkg.tar.gz                      # read what came out
```

Report done only after all four pass and the archive has been read. A package
that fails `plan` fails in CI the same way. A probe that says `unreachable` is
not a pass: a proxy error can hide a real 404, so re-check that URL directly.

## Establish the facts before writing anything

**Feed packages** — ask the feed, per architecture, through the same resolver
the build uses:

```bash
python3 scripts/feed_lookup.py --nest ../pica-nest --mgr apk qbittorrent luci-app-qbittorrent luci-i18n-qbittorrent-zh-cn
```

It prints version, subdirectory and real filename per arch, and which arches
lack a name. The matrix is the arches that carry **every** required name.

**GitHub releases** — list the raw asset names; a rendered page mangles them:

```bash
curl -s "https://api.github.com/repos/OWNER/REPO/releases/tags/TAG" | python3 -c \
  'import json,sys; print("\n".join(a["name"] for a in json.load(sys.stdin)["assets"]))'
```

**Binaries** — decide libc, endianness and arch from the file, not its name.
OpenWrt is musl: a `linux-aarch64` glibc build downloads fine and does not run.
`references/habits.md` has how to check.

**Dependencies** — from the upstream control/recipe, never from the name:

```bash
tar -xzOf pkg.ipk ./control.tar.gz | tar -xzOf - ./control | grep -E '^(Package|Version|Depends|Architecture)'
curl -sL "https://raw.githubusercontent.com/OWNER/luci/master/applications/PKG/Makefile"   # LUCI_DEPENDS
```

## Choose the backend and the source

| Upstream ships | `<mgr>` | `source.type` |
|---|---|---|
| A package in an ImmortalWrt / OpenWrt / other configured feed | `opkg` or `apk` | `feed` — names only |
| ipk/apk files on a GitHub release | `opkg` or `apk` | `github` — regex per asset |
| ipk/apk at a fixed URL outside any configured feed | `opkg` or `apk` | `url` |
| A tarball or bare binary, no package | `pica` (or `opkg` + scripts) | `archive` — unpacked into `root/` |

Prefer `feed` whenever a configured feed carries the package: no filename or
version is written anywhere, and moving to a new ImmortalWrt release is one line
in `ci/config.json`. A new feed goes into `ci/config.json` `feeds`, never as a
URL in a build.json. Prefer a release directory over a snapshot or branch feed:
those move in place and keep no history.

`pica` carries no container and installs no dependency: `base`/`app`/`kmod` on a
`pica` target are refused. A package for two backends scopes its dependencies:
`base@opkg = bash`. Field-by-field detail for every source type is in
`references/sources.md`.

## Versions

- `feed` and `github` jobs **omit `pkgver`**: it comes from upstream, per
  architecture, normalised for publishing (`~` → `.`, feed `-rN` dropped).
- `url` and `archive` jobs **must pin `pkgver`** and write `{version}` in the URL;
  `"upstream": "github:owner/repo"` lets `nest bump` move it.
- A github job may pin too (`"tag": "v{version}"`); then the build fails loudly
  when upstream moves on, and the daily bump opens a pull request.
- `pkgver` never contains `~`; a `-` needs an explicit `pkgrel`.
- A published filename is immutable. To republish changed `scripts/`, `root/`
  or manifest under the same version, bump `pkgrel`.

`references/naming.md` has the filename and the three names that are not it.

## Declare every container

The build reads each downloaded container's own metadata and stops when one
installs a name the manifest does not declare — including **optional** assets.
`app = luci-app-argon-config?` declares one that may be absent.

A required name that a feed carries moves the whole install to the feeds;
mark such shared dependencies optional: `base = luci-base?`.
`references/habits.md` has the policy in full.

## Rules `nest validate` enforces

- the directory is `packages/<mgr>/<id>/`, `<mgr>` is in `targets`
- manifest has `pkgname` `appname` `os` `targets`; no `pkgmgr` `platform` `arch`
  `builddate` `size` `source`; `source_availability` (not `visibility`) is
  `open|partial|closed`
- matrix arches are keys of `ci/config.json` `platforms`; `all` stands alone
- `feed` names a configured feed; `url`/`archive` pin `pkgver`; `{version}` only with a pinned `pkgver`
- github `match` compiles and has at most one group (the arch)
- a `pica` target reads no unscoped dependency
- nothing but `manifest build.json scripts/ root/` in the package directory
- no archive or large file tracked by Git

## After the build

Read the archive: every declared container present, executables `+x`, nothing
stray under `root/`. Then check the output for `note:` lines — a container whose
metadata could not be read (apk-tools 3.x) is *unverified*, not passed.

When CI reports a failure, `references/habits.md` lists the ones seen so far
with their cause; most are a matrix arch upstream does not build, an undeclared
container, or an upstream that moved past a pinned version. A package that
failed is retried by the daily upstream workflow once `nest outdated` sees it
missing from the index — fix it and push, or wait for the next run.
